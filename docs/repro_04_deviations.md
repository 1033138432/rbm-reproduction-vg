# 复现的偏差与局限

> 哪些对齐了、哪些没对齐、哪些根本没法对齐。

## 一、无法对齐的部分（最重要）

### 1.1 初始条件不同 → 绝对值不可比

| 项 | 原项目 | 本次复现 |
|---|---|---|
| 初始姿态 | 环境默认（`robot_init_pose_seed`）| **从演示导出的 `*_state0.npy` 注入** |
| 原因 | — | 本机 `robot_init_pose_seed` 无效，不注入则 rollout 全 0（0/12）|

**结论**：两套初始条件不同，**成功率绝对值不可直接比较**。
能比较的只有"同一初始条件下不同模型的相对排序"。

### 1.2 实测数字与原项目文档的差异

本次复现（协议已经确定）：

| 模型 | 协议 | 成功数 |
|---|---|---|
| 官方 BASE | A（openpi RHC-10 闭环）| 76.7%（69/90）|
| 官方 BASE | B（RLinf 开环 50 步）| 55.6%（50/90）|
| 本次 SFT | A | 56.7%（51/90）|
| 本次 SFT | B | 27.8%（25/90）|
| BASE（OOD）| B | 2/60 |
| SFT（OOD）| B | 2/60 |

原项目文档（**用的是哪套协议未说明**，不能和上面的 A 或 B 直接配对）：

| 模型 | 成功数 |
|---|---|
| 官方 BASE | 47.8%（43/90）|
| SFT | 74.4%（67/90）|
| BASE（OOD）| 5/60 |
| SFT（OOD）| 2/60 |

本次 BASE 更高、SFT 更低，方向与原项目相反。可能原因：
1. 初始姿态注入让 BASE 占了便宜（它更依赖初始姿态）
2. SFT 训练超参不同（本次 20k 步 / expert-only；原项目未写清）
3. 原项目没写清用的是哪套评测协议（A 闭环、B 开环相差 20+ 个百分点），数字本身可能不同口径

## 二、用代理指标替代的部分

| 原本要做的 | 实际做的 | 影响 |
|---|---|---|
| 全量 RECAP（含专家 correction + value pipeline）| **RECAP-lite**（advantage 条件化 CFG-SFT）| 中：不是完整算法 |
| Proxy mix 训练 | **未做** | 中：少一个消融 |
| Action trace 对齐（逐帧对比 JAX/PyTorch 输出）| **未做** | 高：无法证明两个后端策略输出一致 |
| 断点续训验证（save→load→继续训）| **未做** | 低：工程性验证 |

## 三、资源限制造成的影响

| 项 | 限制 | 后果 |
|---|---|---|
| 磁盘 | 两次写满（100%）| PPO 断点曾被截断（`failed finding central directory`），重训一次 |
| 内存 | cgroup 120 GB | 192 个孤儿 `pt_data_worker` 占满 115 GB，训练进程被内核杀 |
| 模型权重 | 复现后为腾磁盘删除（SFT 34.7 GB / PPO 19 GB）| **无法再复现评测**，需重新训练 |

## 四、结论的适用范围

### 能得出的结论

- 完整跑通 SFT → PPO → RECAP-lite 链路，每一步都有实测数据
- 定位并修复上游一个真实 bug（观测刷新），有前后对照（0/12 → 4/12）
- 数据转换性能优化 31 倍（140 ms/帧 → 4.4 ms/帧）
- 测出两套协议下四个模型的完整数字

### 不能得出的结论

- ❌ "复现了原项目的 74.4%"
- ❌ "本次 SFT 达到原项目水平"
- ❌ "PPO 显著提升了性能"

**正确说法**：在同一初始条件下测得的相对排序是 PPO ≈ RECAP ≈ BASE > SFT，
但绝对值与原项目不可比。

## 五、尚可继续的方向（未执行）

1. **全量 RECAP**：加入专家 correction 与完整 value pipeline
2. **Action trace 对齐**：逐帧对比 JAX 服务与 PyTorch rollout 的输出差异
3. **Proxy mix 消融**：验证混合训练数据对 OOD 的影响
4. **多随机种子**：每个配置 2–3 个种子，给出置信区间
5. **OOD 专项**：所有模型 OOD 都接近全败（2–4/60），值得单独研究
